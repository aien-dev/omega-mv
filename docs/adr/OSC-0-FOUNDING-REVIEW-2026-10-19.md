## Summary for Drake (the two questions)

1. **Was Omega founded correctly?** Yes, for what it set out to do: make a programming language in which whole classes of memory mistakes cannot be written. The rules were tested before any compiler existed (a million random cases, zero misses), the compiler slices that followed obey them, and three weeks later Omegese, the AI's language, was built on the same foundation without changing it. That is the strongest sign the foundation was laid well.
2. **Your worry about decision 3 is unfounded.** "Linear" there means "each completion ticket can be used exactly once", not "one job at a time". Nothing in OSC-0 limits how much work runs at once.
3. **But the engine does run one GPU job at a time today**, for a different reason: the GPU session was built with one work queue and one lock (`src/omega_gpu_session.h:29-33`). OSC-0 never decided how much should run in parallel. That is the biggest gap for the mission.
4. **What you could have done better.** Two things. First, the founding audit measured everything except GPU speed (audit I.10 lists "GPU workloads" and "throughput and latency" as not measured), so no founding decision was ever judged on speed. Second, the order you set (audit, freeze, compiler slice, then move old C code across, starting with the crumb log reader) aimed the language at the operating-system code, not at the language model. Three weeks on, the compiler still has no decimal numbers (no floats) and arrays of at most 64 items, so it cannot yet express a single line of the model's arithmetic. Neither was a mistake on 2026-09-29, when the language model was not yet declared the priority; both should be corrected now.
5. **What to change:** keep all eleven decisions; amend three (9, 10 and the identity-break timing); add four new ones (12 to 15): how much GPU work runs at once, the AI as the writer, the model's language subset first, and energy as a measured result.

## Terms used once and then freely

- **OSC**: Omega Systems Core, the safe programming language Omega compiles. **oscc** is its compiler.
- **Omegese**: the language the AI writes; it translates into OSC's internal form.
- **Compiler slice**: a small, working piece of the compiler, finished end to end before the next.
- **IR** (intermediate representation): the compiler's internal, checked form of a program, between the text and the machine code.
- **Fence**: a ticket the GPU's work produces when it finishes. **Quiesced**: proof that a device has stopped touching some memory.
- **Linear** (decision 3): a value that must be used exactly once, never copied and never forgotten. A Fence is linear so the same finished job cannot be used twice to free the same memory twice. Example: start a hundred GPU jobs at once and you hold a hundred tickets; each ticket frees only its own job's memory, and only once. Linear limits how often a ticket is used, not how many jobs run.
- **Channel / queue**: a line of GPU work the processor works through in order. Several channels can run side by side.
- **Oracle**: a trusted second implementation used only to check answers, never shipped.
- **Ceiling**: the hardware's physical limit (bytes per second from memory, operations per second). **TY-7**: bits of TURING Yield per wall joule.

## 2. What OSC-0 does not decide and the mission needs

The mission (Drake, 2026-10-19): the compiler exists first to run the language model on our own engine, and needs only that plus calculations and meaning; one seed builds the whole system and gcc, rustc and the GNU tools become reference oracles and then leave; Omegese is the AI's assembly language, made unable to be malformed by the next-word mask, growing into the model's language of meaning, with promises inside the same mask; and the score is physical: fraction of the hardware ceiling, and TY-7.

OSC-0 was written three weeks before most of that. Its context paragraph says what it was for: replacing "about 98k lines of C and assembly" in Omega, PHYSICS and AIENOS (`OMEGA-SYSTEMS-CORE-0000.md:10`). Four things follow.

**Throughput.** Decision 3 is about safety only. Today one decode token of the 30B model is one recorded list of 436 GPU launches (`src/omega_gpu_decode_graph.h:25`) sent down one channel, and every caller waits on one lock: "Calls from several threads therefore serialise on the device; that is the documented model (one channel, one GPFIFO)" (`src/omega_gpu_session.h:29-33`). Each launch runs many GPU threads, so the chip is not idle inside a launch, but copying, computing and the next token never overlap. Nothing in OSC-0 asks how many channels, queues or batched requests should be in flight, or how memory transfer and arithmetic overlap. A language model's speed against the ceiling depends mostly on exactly that.

**The AI as the writer.** OSC-0 assumes a human writes OSC text. Omegese now feeds the same IR and the same checker unchanged (`tools/omegese/omegese.c:3-4`), and its `next` command is the mask an engine applies while the model writes (`omegese.c:14-17`). The founding never says that the AI's form is the main surface, that every language feature must exist as a word in the mask, or that promises (D3) must be inside it. The mask is not yet wired into Omega's engine code (no mention of Omegese under `src/`).

**The model's subset.** OSC-0 aimed at a general systems language for kernels and drivers. The model needs a narrower and different set: decimal numbers and small formats (f32, bf16, fp8), large buffers, matrix and vector shapes, GPU launch and record words, a decode loop that runs indefinitely, sampling and the mask. Today OSC has integers only (`src/compiler/osc_ir.h:44-54`), arrays of at most 64 items (`osc_ir.h:37`), loops of at most a million turns (`src/compiler/osc_parse.c:11`), and the floats design is written but not built (`docs/osc/OSC-4-DESIGN.md:3`). The 10,750 lines of GPU engine code (`src/omega_blackwell_*.c`) and the decode graph are C, compiled by gcc.

**Energy.** OSC-0 has no measure of speed or energy at all, and its baseline left GPU work and throughput unmeasured (audit I.10, "Not measured"). Energy tooling now exists outside the compiler (`tools/ty_energy_run.sh`), but no compiler gate reads it.

## 3. Proposed decisions (in the style of the ADR)

12. **PROPOSED. Concurrency for throughput.** The engine declares how many GPU channels and queues are in flight, and transfer, arithmetic and the next token overlap wherever the data allows. Each in-flight piece of work holds its own Fence; reclaim consumes only its own Fence (decision 3 unchanged). The single process-wide lock and single channel become a measured choice, not the default. **Gate:** (a) the II.11 model extended with several channels and Fences outstanding at once, 10^6 seeded sequences, zero false accepts; (b) a decode run on the Spark reporting tokens per second and bytes per second as a fraction of the memory ceiling, single channel against the overlapped design, same tokens out bit for bit.

13. **PROPOSED. The AI is the writer.** Omegese is the main way programs are written. A feature is not finished until it has an Omegese word, a `next` mask entry and a translation into the IR; `requires` / `ensures` are words in the same mask, so a program the mask accepts carries its promises. **Gate:** the mask fuzz over every prefix includes the promise words; every program the mask completes is accepted by the checker and its promises are enforced (trap 9 or 10 on a planted violation); the mask runs inside the engine during generation.

14. **PROPOSED. The model's subset comes first.** Before any kernel, driver or crumb-log migration, OSC and Omegese gain what the decode path needs, in this order: f32 and the storage formats bf16 and fp8; large buffers; GPU launch, record and Fence words (using 4 and 8); an indefinitely running serve loop with a bound per token; sampling; the mask. The general systems subset follows. **Gate:** one decode token of the current model whose host program is compiled by oscc from Omegese gives the same tokens as today's C host path on a fixed prompt, and its speed is reported against the ceiling.

15. **PROPOSED. Speed and energy are measured results.** Every compiler milestone that touches a run-time path writes, in its receipt, the fraction of the hardware ceiling and TY-7 measured on a quiet machine, next to the previous receipt. "A milestone never passes on source code existing alone" (audit III.7) is extended: a run-time milestone never passes on correctness alone. **Gate:** the receipt writer refuses a run-time receipt without both numbers, and a test proves the refusal.

Amendment to 9 (and 10), stated with them in section 1: the compiler-built-by-compiler chain starts at seed-0, and gcc, rustc and the GNU tools act only as comparison oracles until they leave.

## 4. Mistakes, stated plainly

**What was sound, and the evidence.**
- The rules were tested before a compiler existed, and the test passed at full size (receipt in row 11). Two days later the first slice was implemented (`docs/osc/OSC-1-DESIGN.md:5`, "Lane 22, 2026-10-01"), so the freeze did not hold the compiler up.
- The contract rule (D3) did its job: enforcement landed before anything migrated.
- The founding's habits spread to code it did not govern: the C GPU session uses generation-checked handles, separate CPU and GPU addresses, and a fail-closed latch on uncertain completion (`src/omega_gpu_session.h:26`, `:49`).
- Omegese, invented three weeks later for a different writer, reuses the IR, the checker and the signed receipt chain unchanged (`tools/omegese/omegese.c:3-4`). A foundation that a new language can stand on without changes was laid well.
- No decision cost time without benefit. Decisions 3, 4 and 8 are unbuilt in OSC, so they have cost nothing yet; the parts that were built (1, 5, 6, 7, 9, 11, D1, D3) each prevent a named failure and are tested.

**What should have been different.**
1. **The baseline left out the GPU.** Audit I.10 measured CPU build times and allocation counts and listed "the GPU/accelerator workloads" and "throughput and latency" as not measured. Because nothing was measured on the GPU, nothing in the founding was ever weighed against speed, and decision 3 could be written as pure safety with throughput left out. This is the one real gap in the founding itself.
2. **The order pointed at the wrong first customer for today's mission.** Audit, freeze, compiler slice, then migration starting with crumbline (audit III.7) is a sound order for replacing operating-system C. For the language model, the slice after the freeze should have been the decode path's arithmetic (floats, large buffers, one GPU launch). Result: the compiler and the engine grew side by side, and none of the engine is OSC (section 2). On 2026-09-29 the language model had not been declared the priority, so this was a reasonable call at the time; it is the main correction now (decision 14).
3. **Smaller:** decision 6's typed errors and decision 2's ban on live handles in records stayed promises because `Result` and the identity break kept moving later. Neither hurts the model; both should be built with 14 rather than separately.

Recommendation: accept 12 to 15 in the order 14, 12, 15, 13 (the model's subset first, because 12 needs GPU words in the language and 15 needs something to measure), and move D4 behind 14.
