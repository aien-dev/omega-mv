# Omega 1.0: readiness audit, milestones and acceptance gates

Status: PROPOSED plan, 2026-10-26. Source audited: `aien-dev/omega-mv` main
`3364a1dfd0ca50c1b82bf19ba34932d8bc10a7a9` (merge of #787). Nothing in this file is a readiness claim.
It records what exists at that commit, what is missing for a 1.0 language and toolchain, and the gate
each milestone must pass before anyone may call it done.

Ownership. Live programme status and sequencing stay with aien-architecture
(`CURRENT_EXECUTION_PLAN.md`, `doctrine/ROADMAP.md`); its `M0..M40` rows are system milestones and are
not renumbered here. This file owns only the language/toolchain acceptance contract for Omega 1.0. Its
milestones are named `RM1..RM11` so they cannot be confused with those rows, with the OM-1/OM-2 language
profiles, or with the R1..R16 runtime ladder. Each milestone has one tracking issue; existing owner
issues keep their scope and are linked, not replaced. The programme issue is
[#599](https://github.com/aien-dev/omega-mv/issues/599).

Evidence words, kept separate everywhere below: PROPOSED, IMPLEMENTED (code exists), EXERCISED (the
changed path ran with expected versus observed results and a negative control), QUALIFIED (the
repository gate for that claim passed at an exact commit), MERGED, DEPLOYED. Verdicts: PASS, FAIL,
NOT_RUN, BLOCKED_HARDWARE, BLOCKED_OPERATOR, MISSING_IMPLEMENTATION. Host and emulator results are never
hardware qualification. Every GPU acceptance step in this file is BLOCKED_OPERATOR until an authorized
exclusive GB10 window runs it; it is never satisfied by a host or simulator run. A head that changes
`.aien/`, `tests/gates/`, `.github/workflows/`, `.forgejo/` or `tools/aien-test/` is BLOCKED_OPERATOR
under `AGENTS.md`, so every "wire into the gate" step below needs that operator run.

## 0. What 1.0 means (bounded)

Omega 1.0 is a release of one named language profile and its toolchain with a written compatibility
promise. It is reached when every RM gate below records PASS at one commit, or when a gate is removed
from the 1.0 scope by an explicit decision recorded in its tracking issue. It does not mean "every
feature anyone may want", and it never means hardware qualification beyond the targets RM9 lists.

| 1.0 includes | 1.0 explicitly excludes unless a recorded decision adds it |
|---|---|
| One frozen source profile (`OM-1.0`, section RM11) that is a superset of today's OM-1 and OM-2 | Shared-memory threads and atomics (FR-6, decision 37 undecided) |
| Executable contracts checked by the compiler or at run time (RM2) | General constant-time or speculative-constant-time guarantees (OM-2 spec section 8) |
| A measured, reproducible efficiency baseline and at least one qualified optimization (RM3) | Packed C-compatible structs beyond `layout` (FR-2) |
| A decided allocation model (RM4), byte/text facilities (RM5), modules (RM6) | Kernel words (FR-8) and a full GPU programming model |
| A versioned FFI with executed callers (RM7), stable diagnostics (RM8) | Universal source conversion (#624 family stays separate work) |
| A declared target set, each with its own gate (RM9) and compiler trust evidence (RM10) | Any claim on hardware the target table does not list |

### 1.3 Findings

1. **The OM-2 contract is cited as normative on main but is not on main.** Fix in this PR: the three spec
   files from `om2/contract` @ `23fc7f5c9`, byte-identical (sha256 recorded in RM1).
2. **Two merged gates run nowhere automatically.** `gate-irwasm.sh` and the OM-2 `gate.om` are absent
   from every manifest, so a regression in OM-2 or irwasm is invisible to `OMEGA-SEED`. Fix is RM1 and
   BLOCKED_OPERATOR (touches `tests/gates/`).
3. **Open compiler defect #775.** An empty `text` passed to `view uchar *` reports the following text's
   bytes (reported count 32 instead of 0, reported on `e623d440` and stated to share main's code).
   Not reproduced in this audit (no builds were run). It is a memory-safety boundary: the callee
   reads bytes it was not given.
4. **Stale status text.** `README.md` line 5 says the seeded compiler is in candidate branches (line
   27 of the same file says it is on main since #696). `OM2-TUTORIAL.md` says the OM-2 stack is draft and
   main compiles OM-1 only. `OM_COMPLETION.md` (2026-10-23) quotes a 7,208-line compiler. `seed/host/README.md`
   says seventy original fixtures; #789 measured 62. This PR corrects the first two and marks the third
   as a dated snapshot; the fourth is corrected inside #789.
5. **Diagnostics are numeric and overloaded.** omc prints `omc: line N: error E`; codes 1..24 and
   27..29 exist (25 and 26 are unused). In `omc.om`, error 7 is raised from 109 sites, 16 from 72 and 9
   from 58, so one number names many different mistakes. `om2 diag` adds machine records
   (`omc-diag 1 ...`) only in OM-2 units.
6. **Capacity and naming limits block real programs.** 512 functions per unit (PR #768 raises to 4096 for
   `aien-math`; a local unpublished x86 branch raises to 1024), 16 registers with no spilling (error 12),
   6 parameter slots, 8-character local names (error 13). These are implementation limits, not language
   rules, and each needs a decision before 1.0 freezes them.
7. **A second target exists only off GitHub.** omega-harness#9 cites commit `7eca2ac3f` ("x86-64 Linux and
   UEFI back ends", 2,043 lines added to `omc.om`) on branch `feat/allen-imac-competition`; that commit is
   not on `aien-dev/omega-mv` (GitHub returns 422 for it). It is IMPLEMENTED, unreviewed, unpublished.
8. **No contracts in the forward compiler.** omc has no `requires`, `ensures` or `assert`; the only
   contract syntax is in the legacy C front end, and OSC IR carries contract text as metadata.
9. **Efficiency is not measured against an optimizing baseline.** The only filed comparison
   (`om/sha256/om2-evidence/s4/measure/RESULTS.txt`) is OM-2 versus OM-1 plus a C adapter; arm C
   (pure C) is NOT_RUN. Hashes of 1 to 55 bytes were 6.5-12.9% slower (declared REGRESSION under the
   predeclared policy; ratios 1.065 to 1.129 in that file).
10. **No heap and no imports by design decision.** Decision 24 (no heap, no `free`) and FR-3 (imports by
   digest, needs the OSC content-addressed unit store) are recorded blockers, not oversights.

## 2. Milestones

Each milestone lists current evidence, the gap, the acceptance gate (all items required), and its
tracking issue. "New gate" means a gate that does not exist yet and is PROPOSED here; its first PASS
must come with a negative control that fails.

### RM1. Ground truth and gate coverage

Current: OM-2 and irwasm are MERGED with author-run evidence only; spec missing from main; #775 open;
#789 open (fail-closed seed/secret gates).

Gap: a single gate run cannot currently show that every merged compiler path still works.

Acceptance:
- `spec/omegese-om2.md`, `-errata.md`, `-measure.md` on main with sha256 equal to `om2/contract`
  @ `23fc7f5c9`: `245bb74e...0881` (contract), `7b8c1ea5...d671` (errata E1..E18), `507702d0...7bad`
  (measurement protocol). This PR carries them and the three digests were checked when copying.
- `OMEGA-SEED` (or a new manifest under the same owner) runs `seed/qualification/om2/gate.om` over
  every `seed/omc/om2/*/*.cases` and `seed/wasm/gate-irwasm.sh`, and fails on `invalid` or `not_run` > 0.
  Negative control: a fixture with a wrong expected status makes the gate exit nonzero. BLOCKED_OPERATOR.
- #775 fixed with a fixture (empty text to `view uchar *` returns `len` 0) and a mutant that restores the
  defect and is killed.
- #789 resolved (merged or superseded) so a missing IR oracle can never yield a qualification PASS.
- `crumb verify .` OK with the tool pinned in `crumb.lock`.

### RM2. Executable contracts

Current: MISSING_IMPLEMENTATION in omc. OM-2 has one built-in invariant (`holds NAME dup32`) with
kept/erased reporting, `fresh` initialization tracking and `layout` checks. The legacy C front end parses
`requires`/`ensures`; IR v6 structured contracts are draft PR #525. Owners: #625 (semantics), #623
(per-lowering validation), #656 (contract-to-.om synthesis), #746.

Gap: a programmer cannot state a pre/postcondition or loop invariant in `.om` and have the compiler
enforce it.

Acceptance:
- A versioned profile section (OMEGESE or `spec/omegese-om3.md`, since OM-2 is frozen) defines contract
  words, their typing, evaluation order, purity rule (no effects, no calls with effects), and trap codes;
  a contract that cannot be checked is a refusal with a named obligation, never silently dropped.
- omc lowers every contract to a runtime check unless a rule stated in the spec erases it; with
  `diag` each check is reported `kept` or `erased` with its rule, as `omc-check` does today.
- Fixtures: each contract kind accepted and violated (trap code and site match), each refusal code, and a
  mutant per erasure rule (erasing a check that the rule does not justify must be caught).
- C1/C2 compatibility: every C2 manifest entry stays byte-identical; units without contracts compile
  identically.
- Function-mode contracts surface through the bridge as a status, never as undefined behaviour (RM7).
- IR mode either carries contracts in a version that checker2 reads, or refuses contract units with a
  named error (no silent omission).

### RM3. Measured efficiency

Current: correctness gates only. Register allocation is a fixed 16-register pool with no spilling;
every float operation moves through v0/v1; OM-2 adds opt-in unroll, inline, folding inside expanded
bodies and constant-index check elimination. A fixed baseline protocol is being prepared on branch
`perf/omc-efficiency-baseline` (`bench/omc_efficiency/PROTOCOL.md`, kernels with C twins, an Omega
conductor, evidence under `evidence/OMC-EFF-1/`); no numbers are cited here until that evidence is
published.

Gap: no predeclared, paired comparison of omc output against an optimizing C compiler on the same
kernels, and no optimization qualified against such a baseline.

Acceptance:
- A frozen protocol (sha256 recorded before data): kernels, input sizes, C twin and compiler flags,
  CPU pinning, interleaved paired arms, warm-up, repetitions, the statistic, and the regression policy.
  Statistics computed with Wolfram and quoted with the query.
- Baseline evidence: per kernel, output equality of the two arms first, then time, code size and compile
  time, all at one omc pin and one host.
- At least one optimization (for example a register allocator with spilling, which also removes error
  12 as a user-facing limit) lands with: C2 manifest byte-identity for units that do not opt in, or a
  declared new pin with all fixtures equal in behaviour; birth fixpoint; a mutant that breaks the
  optimization and is caught; a paired A/B against the baseline under the same frozen protocol.
- Compile-time and compiler-memory bounds stay linear in output (OM-2 section 4 rule) and are gated.
- Results labelled MEASURED HOST AArch64; no GPU or cross-machine performance claim.

### RM4. Memory model: heap and allocation

Current: decision 24 forbids a heap and `free`. Storage is stack `new` (4 MiB per function), `global`
pools (1 GiB total), process-local mappings through `mapnew`/`maphold` (128 slots, up to 64 GiB each,
accessed only through copy words). OSC IR v2..5 already specify arenas, pools and generation-checked
heap operations, but only in C. Related: #756 and draft PR #771 (bounded quantities and object
slices), #705, #759.

Gap: programs whose working set is not known at compile time (parsers, interpreters, `aien-math`)
must preallocate global pools or use mapping copies.

Acceptance:
- BLOCKED_OPERATOR until Drake records a decision: keep decision 24 (and document pools plus
  mappings as the 1.0 model with sizing guidance), or replace it with a named model. Options with
  existing specs: region/arena with whole-region release; generation-checked handles matching IR
  `HALLOC/HGEN/HFREE` so checker2 can validate the lowering.
- If a model is adopted: use-after-release, double release and stale generation are refused at
  compile time or trap with a named code before any access; exhaustion returns a status, never an
  overrun; fixtures, mutants that remove each check, and a fuzz differential against an independent
  model.
- Allocation is never implicit: no hidden allocation in any existing word (C1/C2 unchanged).
- Bounded quantities (#756): lengths, offsets and counts do not wrap silently; the
  `(2^64-8)+16` counterexample in #756 is refused before addressing.

### RM5. Strings and text

Current: `text NAME "bytes"` read-only literals (program mode only), `uchar` arrays, explicit lengths,
no terminators. OM-2 unsized views (`view uchar *`) and `part` give checked slices; this resolves the
"open arrays" blocker of `OM_COMPLETION.md` item 4 for parameters. There is no UTF-8 handling, no
number/text conversion, no formatting word, no comparison or search library. #775 is a defect in this
path. Consumers that need more: #788 (TLS/HTTP/JSON proposal), omega-bridge text constants
(unsupported by its converters).

Acceptance:
- A seeded `.om` text unit (byte compare, search, split, decimal and hex integer parse/format with
  range refusal, UTF-8 validation with rejection of overlong, surrogate and out-of-range encodings),
  callable from OM-1.0 units, with no new compiler word unless one is proposed and gated.
- Differential tests against an independent oracle on fixed and seeded random inputs, including
  empty, maximal and invalid inputs; UTF-8 vectors cite their source.
- Text in function mode: either supported with a stated ABI (RM7) or refused with a named error.
- #775 closed (RM1).

### RM6. Modules and separate compilation

Current: no `import`; units compose by concatenation. OM-2 adds `export fn` (up to 32 entries) and
links separately compiled units only through bridge symbols that embed source sha256, omc pin and
profile. FR-3 (imports by digest) is blocked on the OSC content-addressed unit store. Capacity:
512 functions per unit on main; PR #768 proposes 4096. Owners: #621, #648, #631.

Acceptance:
- A decided module form: digest-addressed import (source sha256 plus compiler pin), with a stated
  visibility rule and a refusal for a missing, stale or mismatched digest. If the unit store remains
  external, the decision records where digests resolve.
- Two separately compiled `.om` modules linked into one program-mode binary and one function-mode
  library, with interleaved calls, matching a concatenated single-unit build in behaviour.
- Negative controls: wrong digest, wrong pin, wrong profile, duplicate export, cycle.
- Per-unit capacities chosen by measurement on the largest real consumer and gated at their boundary
  (accept N, refuse N+1 with error 14), as gate12/gate15 do today.

### RM7. omega-bridge FFI

Current: ABI v1 (`omega_<name>`) and v2 (`omega2_<name>`, unsized views, `out` buffers, status 32
refusal before Omega code runs, status 33 reentry). omega-bridge main `adb26cc6` prints
`NATIVE-CALL PASS` only after seven callers (`c`, `c-bti`, `cpp`, `python`, `rust`, `zig`, `go`) build
and run. omega-mv pins the older `431fff0a`. Unsupported by contract: forged lengths, read-only memory
passed as edit, stack exhaustion (faults, not a status). Not present: shared objects and a general C
ABI (FR-7), callbacks into foreign code, floats and text through the C/Python converters.

Acceptance:
- `om/omega-bridge.lock` at a bridge commit whose `tests/native/run.sh` printed `NATIVE-CALL PASS`, with
  `tests/native/test_build_failures.sh` showing FAIL and NOT_RUN for injected and missing toolchains.
- `tests/gates/run.sh om-units` PASS at that lock; regenerated binding byte-identical.
- An ABI version document listing every supported parameter kind, status code and failure mode, with
  one executed refusal case per status and a version-mismatch case that fails at link time.
- Each RM2 contract violation and each trap reaches a caller in every qualified language as a status.
- Decision recorded on FR-7 (shared objects); if adopted, symbol versioning and a dlopen caller are
  exercised in each language.

### RM8. Diagnostics and error messages

Current: one human line per refusal, numeric code only. gate15 pins codes 3..23 with one minimal
program each (21 cases); 27..29 have OM-2 fixtures under `seed/omc/om2/` and 24 the #669 work, none of
them in gate15. Machine records exist only in OM-2 `diag` mode (#655 owns incremental feedback).

Acceptance:
- A code registry in the language doc: every code, its meaning, the obligation, and one minimal
  refusing fixture each, with gate15 extended to every code (including 24, 27, 28, 29).
- Overloaded codes split or given a stable sub-reason in the machine record, so each emitting site in
  `omc.om` maps to exactly one documented reason; a coverage check lists any emitting site without a
  fixture.
- A human-readable message for each code (stderr text, still one line), with stdout unchanged and the
  existing `omc: line N: error E` prefix preserved for current consumers.
- Diagnostic records available in every profile of 1.0 (not only `om2 diag` units), keyed to the input
  sha256 and compiler pin.

### RM10. Compiler trust and C retirement

Current: birth fixpoint, om4 as referee, `seed/check/audit2.sh` instruction referee, C referees for
gate-ir, gate17 differential fuzz against the pinned compiler. Open: #650 diverse double compilation,
#669 branch displacement (long backward reachability not yet established), #725 retiring handwritten
seed hex, #726 removing the legacy C compiler only after consumer cutover (drafts #761, #762, #763,
#765, #751 port parts of it).

Acceptance:
- #650: an independently built compiler path reproduces `seed/out/omc` byte for byte, with the
  independence argument written down; a planted miscompile in one path is detected.
- #669 closed with every branch form and displacement extreme covered.
- #726: each removed C component has a qualified `.om` replacement, its consumers cut over, and an
  active-tree audit showing no fallback remains; the C referees that gates still need are declared as
  qualification oracles outside the delivered closure, per #599.

### RM11. Stability guarantee

Current: profiles are frozen documents (OM-2 says a change needs `omegese-om3.md`); the C1 (meaning)
and C2 (bytes, per manifest entry) compatibility rules exist for OM-1 to OM-2 only. The compiler pin
changes with every compiler commit and consumers pin by hash. There is no versioned release and no
deprecation policy.

Acceptance:
- `OM-1.0` profile document: the union of OM-1, OM-2 and the RM2/RM5/RM6 additions that pass, with
  every word, limit and code; anything not in it is unsupported.
- Written promise for 1.x: a 1.0 program keeps its verdict, error code and line, stdout, exit status,
  trap code and order (C1) on every later 1.x compiler; machine-code identity (C2) is promised only
  where stated. Changes outside the promise need a new profile.
- A conformance suite (the C2 manifest plus RM1..RM8 fixtures) that every 1.x compiler must pass,
  run in the gate set.
- A tagged release: omc binary sha256 recorded before any rebuild, source commit, birth log, and the
  gate receipts of RM1..RM10, content-addressed under `evidence/`.

## 3. Order

RM1 first: it makes every later gate meaningful. RM8 and RM6 decisions early, because RM2, RM5 and
RM7 add codes and boundaries. RM4 waits on Drake's decision; RM5 does not depend on it for 1.0 if the
text unit uses caller-provided buffers. RM3's baseline can run now; its optimization step waits for RM2
so contracts and optimization do not edit the same compiler paths at once. RM9 and RM10 run in
parallel on disjoint paths. RM11 is last and freezes only what passed.
